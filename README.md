# Анализатор рисков оттока

Панель для маркетолога, которая отвечает на три вопроса:

- **кому** из клиентов нужно внимание: risk-score 0–100, уровень (высокий / средний / низкий / нет оценки) и рекомендованное действие;
- **почему**: признаки, которые сработали, вклад каждого в оценку и разбивка «что создаёт риск» по всему портфелю;
- **сколько** денег бизнес может потерять за горизонт прогноза, с учётом цен услуг, балансов, платёжеспособности и риска.

## Запуск

```bash
docker compose up --build
```

| Что | Адрес |
|---|---|
| Панель | http://localhost:8080 |
| Swagger | http://localhost:8000/api/v1/docs |
| Метрики Prometheus | http://localhost:8000/metrics (с токеном, см. ниже) |
| Prometheus (уже собирает метрики и считает алерты) | http://localhost:9090 |

Вход: **admin / admin**.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `ADMIN_USERNAME`, `ADMIN_PASSWORD` | admin / admin | учётная запись панели |
| `JWT_SECRET` | change-me-in-production | подпись токенов |
| `METRICS_TOKEN` | churn-metrics-token | `/metrics` отвечает только на `Authorization: Bearer <токен>`; тот же токен в `deploy/prometheus.yml`. Пусто — метрики открыты |
| `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET` | пусто | вход через OIDC (бонус ТЗ). Пока не заданы, кнопки SSO нет |
| `OIDC_PROVIDER_NAME`, `OIDC_REDIRECT_URL` | SSO, пусто | подпись кнопки и адрес возврата (по умолчанию строится из адреса панели) |

При первом старте загружаются тестовые данные из `data/data.json`. В них статусы услуг выданы по кругу, поэтому у 60 из 97 клиентов есть услуга в `prolong_wait`, просроченная на месяцы, и большинство честно попадает в высокий риск. Для наглядности рядом лежит `data/data_realistic.json` (300 клиентов, статусы в долях живой базы хостинга, цены зависят от периода оплаты, сгенерирован `data/generate_realistic.py`): его можно загрузить на странице настроек или через `PUT /api/v1/source/snapshot`, и распределение станет примерно 25 / 18 / 52 по уровням. Настройки модели, снимок данных, журнал переходов и сессии лежат в томе `churn-data` и переживают перезапуск. Сбросить всё к исходному состоянию: `docker compose down -v`.

## Сценарий демонстрации

1. **Обзор.** Сверху: сколько можем потерять, распределение по уровням, топ-10 в зоне риска с рекомендованным действием, график оттока (факт и прогноз), таблица «что создаёт риск» по признакам, разбивка потерь по периодам оплаты и последние изменения в данных.
2. Клик по клиенту открывает **карточку**: score, ожидаемые потери, платёжеспособность, блок «что делать», список причин с вкладом каждой (вес × сила), разбивка по услугам с ближайшим списанием и история изменений его услуг.
3. **Настройки модели.** В режиме «применять сразу» подвинь вес признака, например «Ожидает оплаты»: через полсекунды плитки, таблицы и карточки во всех открытых вкладках пересчитаются без перезагрузки. В режиме «что-если» те же ползунки считают сводку на копии и показывают разницу с текущей моделью, в модель изменения попадают только по кнопке «Применить».
4. **Исходные данные.** Загрузи JSON в формате `data/data.json` целиком или догрузи только изменившиеся записи (upsert по id). Изменения статусов и автопродления попадают в журнал, оценки и график пересчитываются сразу.
5. Перезапусти бэкенд: коэффициенты, данные, журнал и вход останутся.
6. **Выгрузка.** На странице клиентов кнопка «Скачать CSV» отдаёт текущий список с фильтрами, действием и главной причиной.
7. **Метрики.** В Prometheus (`:9090`) видны те же цифры, что в панели, и пять правил алертов.

## Модель

Модель объяснимая: правила и веса, без обучения. Исторических данных о статусах нет, поэтому обучать её не на чем. Зато каждое число можно разложить на причины.

### Признаки

Каждый признак считается для отдельной услуги клиента. Он возвращает силу сигнала от 0 до 1 и текст причины.

| Признак | Базовый вес | Сила сигнала |
|---|---|---|
| Ожидает оплаты (`prolong_wait`) | 0.90 | от 0.6 в первый день ожидания до 1.0 в день удаления (через 5 дней) |
| Не хватает средств (`insufficient_funds`) | 0.70 | доля продлений в горизонте, на которые не хватит денег |
| Истекает без автопродления (`expiring_without_autoprolong`) | 0.60 | растёт к 1, когда до конца срока остаётся меньше 7 дней; просроченные услуги дают 1 |
| Неоплаченные продления (`failed_payments`) | 0.35 | доля неоплаченных `prolong`-транзакций услуги за последние 90 дней (`paymentLookbackDays`): старая история шумит, а не предсказывает |
| Сервер выключен (`suspended`) | 0.30 | 1, если услуга в статусе `suspended` |
| Уже удалял услуги (`deleted_services`) | 0.20 | доля удалённых услуг клиента |
| Есть заблокированные услуги (`blocked_services`) | 0.15 | доля заблокированных услуг: конфликт с платформой, а не неуплата, поэтому вес отдельный |
| Ни разу не продлевал (`never_renewed`) | 0.30 | 1, если услуга старше одного периода, выполненных продлений нет, автопродление выключено |
| Крупный клиент на нуле (`big_spender_drained`) | 0.35 | 1 − деньги/цена, когда пополнений за всё время не меньше `bigSpenderThreshold` (€1000), а на ближайшее списание не хватает |
| Новый клиент (`new_customer`) | 0.25 | 1 − возраст/`newCustomerDays` (30), возраст от самой ранней услуги; даты в будущем игнорируются |
| Несколько продлений подряд (`renewal_cluster`) | 0.25 | доля суммы продлений живых услуг в окне ±3 дня, которую не покрывают доступные деньги |
| Давний клиент с автопродлением (`long_tenure_autoprolong`), **защитный** | 0.30 | 1, если активная услуга старше `loyalTenureDays` (180), автопродление включено и денег на два периода; снижает риск |

Четыре последних рисковых признака на тестовом наборе почти не срабатывают: цены услуг там до €10 при балансах в сотни евро, а у каждого аккаунта есть услуга возрастом 400 дней. Они рассчитаны на реальные цены и возраст аккаунтов, и это стоит сказать жюри прямо. Защитный признак ограничен статусом `active` намеренно: услуга в `prolong_wait` с включённым автопродлением это сбой оплаты, а не лояльность.

**Нехватка средств** считается по плану списаний. Продления всех живых услуг клиента в горизонте прогноза выстраиваются по времени. Затем доступные деньги (основной баланс и бонусы, если они разблокированы) списываются по порядку. Если денег не хватает, у тех услуг, где кончились деньги, срабатывает признак.

Веса подобраны по тому, насколько близко событие к фактической потере. `prolong_wait` — это уже неоплаченная услуга, которую через несколько дней удалят. Нехватка денег и выключенное автопродление — следующий шаг до неё. Неоплаченные платежи, выключенный сервер и прошлые потери — косвенные сигналы.

### Формула

```
риск услуги  = (1 − ∏(1 − вес × сила))  ×  ∏(1 − вес × сила защитных)
score        = 100 × max(риск услуг клиента)
лояльность   = 100 − score
```

Риски складываются как независимые вероятности: два сильных сигнала дают риск выше каждого из них по отдельности, но не больше 1. Защитные признаки умножают риск на понижающий множитель; если рисковых сигналов нет, они не показываются, потому что снижать нечего, и в разбивку потерь по признакам не входят. Score клиента берётся по самой рискованной услуге, потому что внимание нужно уже из-за одной такой услуги.

Уровни: **высокий** при score ≥ 70, **средний** при score ≥ 40, иначе **низкий**. Если у клиента нет ни одной живой услуги (`active`, `suspended`, `prolong_wait`), оценки нет, и панель пишет это явно.

### Приоритет и действие

**Зона риска** — клиенты с высоким и средним уровнем; в панели это отдельный сегмент (`level=high,medium` в API), с него начинается обзор и список клиентов. В тестовом наборе у 60 из 97 клиентов есть услуга в `prolong_wait`, поэтому большинство честно попадает в «высокий», а верхушка рейтинга по score состоит из одинаковых 97 баллов. Чтобы внутри зоны был порядок, при равном score выше тот, у кого больше ожидаемые потери: **риск × деньги** как второй ключ, а сортировка по потерям напрямую доступна одним кликом по колонке.

К каждому клиенту модель прикладывает **рекомендованное действие** по самой сильной причине (`backend/risk/actions.py`): напомнить об оплате, предложить пополнение, включить автопродление, проверить способ оплаты, выяснить причину выключения, удержание через поддержку, разобрать блокировку. Если денег не хватает, а бонусы клиента заблокированы, действие одно: разблокировать бонусы, это дешевле скидки.

### Денежная оценка

```
выручка услуги за горизонт = цена × горизонт / длительность периода оплаты
платёжеспособность клиента = доступные средства + средний темп пополнений × горизонт
выручка клиента            = min(Σ выручка услуг, платёжеспособность)      распределяется по услугам пропорционально
ожидаемые потери           = Σ риск услуги × выручка услуги
```

В оценке учтены все три составляющие из ТЗ. **Стоимость услуг** входит через выручку. **Балансы** работают дважды: через план списаний (чем меньше денег на ближайшие продления, тем выше риск) и через платёжеспособность. **Риск** выступает вероятностью потери.

Почему нужен потолок по платёжеспособности: почасовая услуга за 30 дней стоит цену × 720, и в тестовом наборе почасовые услуги давали 99 % «выручки», которой клиенты с балансом в сотни евро никогда бы не заплатили. Больше, чем клиент способен заплатить, бизнес не получил бы и без оттока. Темп пополнений берётся как `totalReplenished / возраст аккаунта`, возраст — от самой ранней услуги. Потолок выключается настройкой `capRevenueByCapacity`; панель показывает и ограниченную выручку, и выручку по прайсу.

Горизонт по умолчанию 30 дней. Все суммы в API указаны в еврокопейках (€1 = 100).

Все веса, пороги уровней, горизонт, окна (истечение, ожидание оплаты, давность неоплат, новый и давний клиент), порог крупного клиента и потолок меняются в панели или через `PATCH /api/v1/model/settings`. Невалидные настройки отклоняются с 422 и на диск не попадают: модель сначала считается с пробными настройками и только после удачного расчёта сохраняет их.

### График оттока

Три ряда по дням (или по неделям, если история длиннее 120 дней):

- **удалено (факт)**: услуги в статусе `deleted`. Дата удаления в данных отсутствует (ТЗ), поэтому берётся конец оплаченного периода, а если переход в `deleted` наблюдал сам анализатор (см. журнал), то реальная дата наблюдения; такие столбцы выделены;
- **услуг под риском (прогноз)**: живые услуги с риском не ниже среднего порога, на дату ближайшего продления в горизонте;
- **ожидаемые непродления (прогноз)**: сумма рисков услуг на ту же дату, то есть ожидаемое число непродлений.

Просроченные события (например, `prolong_wait`, истёкший год назад) ждут «сегодня», а не в прошлом, поэтому прогноз всегда правее линии расчёта. Прогноз считается моделью при каждом пересчёте и меняется вместе с весами.

### Журнал переходов

Источник отдаёт только текущее состояние. При каждой загрузке (полной или частичной) новый снимок сравнивается с предыдущим, и изменения статусов и автопродления записываются в журнал с временем наблюдения. Журнал виден на обзоре, в карточке клиента и через `GET /api/v1/analytics/journal`; из него график берёт реальные даты удалений.

## Архитектура

```
браузер ──► nginx (frontend) ──► FastAPI (backend) ──► модель backend/risk
              статика React        /api/v1, /metrics      evaluate / summarize / timeline
              прокси /api           SSE /api/v1/events
                                   хранилище: память + JSON в DATA_DIR
Prometheus ──(bearer-токен)──────► /metrics  + правила алертов deploy/alerts.yml
```

- **`backend/risk/`** — модель. `features.py` содержит признаки, `scoring.py` — расчёт оценок, сводку, план списаний, платёжеспособность и график, `actions.py` — рекомендованные действия, `defaults.py` — настройки и их проверку.
- **`backend/models.py`** — структуры исходных данных: аккаунты, услуги, транзакции.
- **`backend/routers/`** — эндпоинты, `convert.py` — единое преобразование структур модели в схемы API. **`backend/services/recompute.py`** — единая точка пересчёта: модель → хранилище → метрики → SSE-событие. Модель считается в отдельном потоке, чтобы event loop не замирал на больших снимках.
- **`backend/services/journal.py`** и **`ingest.py`** — журнал переходов и частичная догрузка (upsert).
- **`backend/repository_file.py`** — хранилище. Запросы обслуживаются из памяти; настройки модели, снимок, журнал и сессии пишутся в JSON и читаются при старте. Интерфейс `Repository` позволяет подставить SQL-реализацию по схеме `data/001_schema.up.sql` без изменений в остальном коде.
- **Пересчёт** запускается после `PATCH /model/settings`, после `PUT`/`PATCH /source/snapshot` и по таймеру раз в 60 секунд. Таймерный пересчёт шлёт событие только если результат изменился, поэтому открытые вкладки не перезапрашивают данные впустую.
- **Живое обновление.** После каждого пересчёта бэкенд шлёт SSE-событие `recalculated`, и панель перезапрашивает данные. Перезагружать страницу не нужно.
- **Авторизация.** Логин и пароль обмениваются на JWT. Сессия хранится на сервере и переживает перезапуск, logout отзывает токен. Без токена все `/api/v1/*`, кроме входа и списка способов входа, отвечают 401. `/metrics` отдаётся сборщику по статическому токену `METRICS_TOKEN`, `/health` отвечает только «жив». Swagger открыт как документация: данных в нём нет, а запросы из него требуют токен.
- **OIDC (бонус).** `GET /api/v1/auth/oidc/login` уводит к провайдеру, `/oidc/callback` обменивает код на userinfo через authlib, находит или создаёт пользователя по `preferred_username` или email и выдаёт ту же сессию и JWT, что и пароль. Токен возвращается панели во фрагменте URL, который не уходит на сервер. Подходит любой провайдер с discovery-документом. Поток проверен в режиме «провайдер не настроен»: кнопки нет, эндпоинты отвечают 404; живой провайдер в комплекте не поставляется.
- **`frontend/`** — React + TypeScript (Vite). Типы ответов описаны в `src/api/types.ts` и повторяют схемы бэкенда.

## API

Полная спецификация — [`openapi.json`](openapi.json). Её же показывает Swagger на `/api/v1/docs`.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/v1/auth/providers` | доступные способы входа (пароль, OIDC) |
| POST | `/api/v1/auth/login` | вход, возвращает JWT |
| GET | `/api/v1/auth/me` | текущий пользователь |
| POST | `/api/v1/auth/logout` | завершение сессии |
| GET | `/api/v1/auth/oidc/login`, `/oidc/callback` | вход через OIDC, если настроен |
| GET | `/api/v1/customers` | рейтинг: `search`, `level` (один уровень или несколько через запятую, `high,medium` — зона риска), `sort_by` (`accountId`, `email`, `balance`, `totalReplenished`, `score`, `expectedLoss`, …), `sort_order`, `limit`, `offset`; при равных значениях выше тот, у кого больше ожидаемые потери |
| GET | `/api/v1/customers/export.csv` | тот же список целиком в CSV (разделитель `;`, BOM для Excel) |
| GET | `/api/v1/customers/{id}` | карточка: услуги, признаки, объяснения, действие, история |
| GET | `/api/v1/analytics/summary` | сводка рисков, денежная оценка, разбивка по периодам и признакам |
| GET | `/api/v1/analytics/churn-chart` | график оттока: факт и прогноз |
| GET | `/api/v1/analytics/journal` | журнал переходов: `account_id`, `service_id`, `limit` |
| GET / PATCH | `/api/v1/model/settings` | коэффициенты и пороги модели, PATCH с пересчётом |
| POST | `/api/v1/model/settings/preview` | что-если: сводка с пробными настройками без сохранения |
| GET | `/api/v1/source/snapshot` | текущие данные |
| PUT | `/api/v1/source/snapshot`, `/snapshot/file` | полная замена исходных данных с пересчётом (JSON в теле или файлом) |
| PATCH | `/api/v1/source/snapshot` | догрузка изменившихся записей, upsert по id, с пересчётом |
| GET | `/api/v1/events` | SSE-поток событий пересчёта |
| GET | `/metrics` | метрики Prometheus |

Пример догрузки одного изменения (услуга 1 удалена):


## Как добавить признак

Достаточно одной функции в `backend/risk/features.py`:

```python
@feature("big_spender_low_balance", "Крупный клиент на нуле", 0.4,
         "Много пополнял, но сейчас денег почти нет")
def big_spender_low_balance( service, ctx ):
    a = ctx.account
    if a.totalReplenished < 100_000 or ctx.availableFunds > service.price:
        return None                                   # признак не сработал
    return Signal(1.0, f"Пополнил {eur(a.totalReplenished)}, доступно {eur(ctx.availableFunds)}")
```

Декоратор регистрирует признак в реестре `FEATURES`. Дальше всё подхватывается само:

- признак участвует в расчёте, в графике и в таблице «что создаёт риск»;
- его вес появляется в `GET /model/settings`, ползунком в панели и меткой в метриках;
- причины с ним видны в карточке клиента и в CSV.

Защитный признак объявляется тем же декоратором с `kind="protective"`: он умножает риск услуги на 1 − вес × сила и в панели помечен зелёной меткой. Новый признак получает базовый вес, а сохранённые веса остальных признаков не теряются. Чтобы у признака было своё рекомендованное действие, добавь строку в словарь `ACTIONS` в `backend/risk/actions.py`; без неё панель предложит «связаться с клиентом» с текстом причины. Если нужен новый параметр модели (окно, порог), добавь его в `DEFAULT_SETTINGS` в `backend/risk/defaults.py` и в `SettingsOut`/`SettingsPatch` в `backend/schemas.py`.

## Как подключить PostgreSQL

Схема и сид организаторов лежат в `data/`. Приложение работает с хранилищем только через протокол `Repository` (`backend/repository.py`): достаточно реализовать его методы поверх asyncpg или SQLAlchemy в `backend/repository_sql.py`, добавить сервис `postgres` в `docker-compose.yml` и ветку `STORAGE_BACKEND=sql` в `build_repository()` в `backend/main.py`. Роутеры, модель и фронтенд не меняются.
