# Анализатор рисков оттока

Веб-панель для маркетолога хостинг-платформы: помогает найти клиентов, которым требуется внимание, понять причины риска и оценить потенциальные потери от непродления услуг.

Система использует аккаунты, услуги и транзакции. Для каждой действующей услуги рассчитывается риск, для клиента — score от 0 до 100, уровень риска, денежная оценка и рекомендуемое действие. Каждую оценку можно разобрать на сработавшие признаки.

Модель основана на правилах и настраиваемых весах. Обучения на исторических исходах нет: score является экспертным индексом, а денежная оценка — сценарием при текущих допущениях модели.

## Быстрый запуск

Нужны Docker Engine или Docker Desktop и Docker Compose v2. Команды выполняются из корня репозитория.

```bash
docker compose up -d --build
```

| Сервис | Адрес |
|---|---|
| Панель | http://localhost:8080 |
| Swagger | http://localhost:8000/api/v1/docs |
| OpenAPI приложения | http://localhost:8000/api/v1/openapi.json |
| Проверка живости | http://localhost:8000/health |
| Prometheus | http://localhost:9090 |
| Метрики приложения | http://localhost:8000/metrics |

Демонстрационный вход: **admin / admin**. Данные клиентов и настройки API требуют Bearer-токен. Метрики в Compose защищены отдельным токеном `churn-metrics-token`.

Адрес панели использует **HTTP**. TLS и доменное имя в базовой конфигурации не настроены.

При первом запуске бэкенд создаёт администратора, загружает `data/data.json` и выполняет расчёт. Следующие запуски используют сохранённый снимок.

```bash
docker compose ps                         # состояние сервисов
docker compose logs -f backend frontend  # логи приложения
docker compose up -d --build              # обновление после изменения кода
docker compose restart                   # перезапуск контейнеров
docker compose down                      # остановка с сохранением данных
```

Снимок, настройки, журнал и сессии хранятся в именованном томе `churn-data` с префиксом Compose-проекта. `docker compose down -v` удаляет этот том и все сохранённые данные; при следующем запуске будет выполнена первичная загрузка.

### Учётные данные и токены

Для своего окружения создайте `.env` в корне:

```dotenv
ADMIN_USERNAME=admin
ADMIN_PASSWORD=replace-with-your-password
JWT_SECRET=replace-with-a-long-random-secret
METRICS_TOKEN=churn-metrics-token
```

Случайное значение для `JWT_SECRET` можно получить командой:

```bash
python3 -c 'import secrets; print(secrets.token_hex(48))'
```

При изменении `METRICS_TOKEN` обновите `authorization.credentials` в `deploy/prometheus.yml`, чтобы сборщик продолжал получать метрики. Не добавляйте файл `.env` с реальными секретами в Git.

Сервис Prometheus в базовом Compose опубликован на порту 9090 без собственной аутентификации. При внешнем развёртывании ограничьте доступ к служебным портам 8000 и 9090, а панель разместите за HTTPS-прокси.

## Возможности панели

- **Обзор:** распределение по уровням, потенциальные потери, топ-10 клиентов в зоне риска, выбор приоритета по score или потерям, график оттока, разбивка по признакам и периодам оплаты, последние изменения услуг.
- **Клиенты:** поиск по email, сегменты высокого, среднего и низкого риска, сегмент без оценки, сортировка в обе стороны, пагинация и CSV с текущими фильтрами. Нажатие на уровень риска в обзоре открывает соответствующий сегмент.
- **Карточка:** оценка клиента, денежные показатели, рекомендуемое действие, причины и защитные факторы, действующие услуги и история изменений.
- **Настройки:** веса признаков, пороги уровней, горизонт, временные окна, способ учёта средств и момент расчёта. Режим «Применять сразу» сохраняет изменения с задержкой 400 мс; режим «Что-если» показывает сводку без сохранения до нажатия «Применить».
- **Исходные данные:** замена снимка или догрузка записей из JSON с пересчётом результатов.
- **Автообновление:** SSE сообщает об изменении результатов, после чего открытые страницы повторно запрашивают данные.

Приложение показывает рекомендацию маркетологу; отправку сообщений, промокодов или изменение услуг оно не выполняет.

## Данные и импорт

В репозитории есть два готовых снимка:

| Файл | Аккаунты | Услуги | Транзакции |
|---|---:|---:|---:|
| `data/data.json` — первичная загрузка | 1200 | 2676 | 23018 |
| `data/data_realistic.json` — дополнительный демонстрационный набор | 300 | 657 | 5594 |

Оба набора синтетические. Распределение риска вычисляется по данным и настройкам, а не задаётся заранее. Изменение файла первичной загрузки не заменяет уже сохранённый снимок: используйте импорт через панель или API.

Формат снимка:

```json
{
  "accounts": [],
  "services": [],
  "transactions": []
}
```

При полной загрузке нужен хотя бы один аккаунт. Примеры полей записей находятся в `data/data.json`.

- Связи: `services.ownerId → accounts.id`, `transactions.serviceId → services.id`.
- Деньги — целые неотрицательные значения в еврокопейках: `1000` означает €10.
- Периоды оплаты: `hour`, `week`, `month`, `quarter_year`, `half_year`, `year`.
- Статусы услуг: `active`, `suspended`, `prolong_wait`, `deleted`, `blocked`.
- Для выполненной транзакции `performedAt` обязателен и не раньше `createdAt`; для невыполненной должен быть `null`.
- При импорте проверяются типы, допустимые значения, даты и существование связанных записей.

**PUT** заменяет снимок целиком. **PATCH** выполняет upsert по ID: заменяет переданные записи и добавляет новые, остальные сохраняет. Это замена записи, поэтому передавайте поля записи целиком, а не только изменённое поле. Для отмены услуги передавайте статус `deleted`; отсутствие записи в PATCH её не удаляет.

При обновлении уже известных услуг журнал фиксирует изменения `status` и `autoProlong`. Время события — момент приёма обновления анализатором. Добавление услуги и изменения остальных полей отдельными событиями не записываются. Журнал ограничен 50 000 событиями по умолчанию.

Дополнительный набор можно сгенерировать без сторонних библиотек:

```bash
python3 data/generate_realistic.py --accounts 300 --seed 1 --out /tmp/churn-demo.json
```

SQL-схема, сид и отдельный генератор находятся в `data/`. Они не участвуют в запуске приложения: PostgreSQL-репозиторий пока не реализован, SQL-артефакты не синхронизируются автоматически с текущим JSON.

## Модель риска

Расчёт находится в `backend/risk/`. Реестр признаков — `features.py`, формулы и агрегация — `scoring.py`, значения по умолчанию — `defaults.py`, рекомендации — `actions.py`.

### Момент расчёта и область оценки

По умолчанию горизонт равен **30 дням**. `referenceTime` определяет опорное время:

- `null` — последнее событие в снимке: максимум среди дат создания услуг и дат транзакций (`performedAt`, а при его отсутствии `createdAt`);
- `"now"` — текущее время;
- ISO-дата — явно заданный момент.

Режим `null` делает демонстрацию замороженных данных воспроизводимой. Для оценки с учётом реального течения времени выберите «Текущее время» в настройках.

Оцениваются услуги `active`, `suspended` и `prolong_wait`. У клиента без таких услуг score и лояльность равны `null`, уровень — `no_data`. Удалённые услуги участвуют в отдельных исторических признаках, но не создают будущую выручку.

### Признаки

Каждая функция возвращает силу сигнала `strength` и объяснение. Параметр `weight` задаётся настройками; `impact = weight × strength` участвует в общей формуле.

| Рисковый признак | Вес | Сила сигнала |
|---|---:|---|
| `prolong_wait` — ожидает оплаты | 0,90 | От 0,6 при наступлении срока до 1 к концу ожидания; период ожидания по умолчанию 5 дней |
| `insufficient_funds` — не хватает средств | 0,70 | Доля нехватки в сумме продлений услуги × срочность первого непокрытого списания |
| `expiring_without_autoprolong` — истекает без автопродления | 0,60 | Растёт к 1 при приближении срока; окно — минимум из 7 дней и половины периода; почасовые исключены |
| `failed_payments` — неоплаченные продления | 0,35 | Доля невыполненных продлений за последние 90 дней; у `prolong_wait` последняя неоплаченная попытка исключается для уменьшения двойного учёта |
| `suspended` — сервер выключен | 0,30 | 1 для выключенной, но оплачиваемой услуги |
| `deleted_services` — уже удалял услуги | 0,20 | Доля удалённых услуг клиента среди непочасовых |
| `new_customer` — новый клиент | 0,25 | Уменьшается от 1 до 0 за первые 30 дней от создания самой ранней услуги |
| `first_renewal` — первое продление | 0,25 | Приближение окончания первого оплаченного периода; работает и с автопродлением, почасовые исключены |

| Защитный признак | Вес | Условия |
|---|---:|---|
| `long_tenure_autoprolong` — давний клиент с автопродлением | 0,30 | Активная услуга возрастом от 180 дней, автопродление включено, доступных средств хватает минимум на два её периода |
| `recent_expansion` — недавно заказал новую услугу | 0,30 | Клиенту от 90 дней, за последние 30 дней появилась действующая непочасовая услуга; защита применяется к активным услугам, не истекающим без автопродления |
| `pays_late_but_pays` — платит в последний момент | 0,30 | Минимум два выполненных продления клиента, не менее половины — в последний день перед сроком или в период ожидания; смягчает ожидание оплаты и истечение без автопродления |
| `reliable_manual_renewer` — аккуратно продлевает вручную | 0,30 | Истекающая услуга без автопродления, минимум три подходящих выполненных продления и нет неоплаченных за 90 дней; сила `min(1, число продлений / 6)` |

Для признаков платёжной привычки сроки восстанавливаются по периодам от даты создания услуги. Оплаты в пределах часа от границы периода не считаются поздними, поскольку могут быть автосписанием.

### Планирование доступных средств

Доступные средства — основной баланс плюс разблокированные бонусы. Реферальный `withdrawBalance` добавляется только при включённой настройке `countWithdrawBalance`.

Продления всех действующих услуг в горизонте выстраиваются по времени, затем общий баланс расходуется последовательно. Для каждой услуги сохраняются сумма нехватки и дата первого непокрытого списания. Так один баланс не используется независимо для покрытия нескольких услуг.

Срочность равна 1 для первого непокрытого списания в ближайшем окне `expiringWindowDays`, дальше линейно снижается до 0,25 к концу горизонта. Будущие пополнения в этом плане не учитываются; услуги без автопродления тоже включены как сценарий средств, необходимых для их сохранения.

### Формула и уровни

```text
impact признака = weight × strength

базовый риск услуги = 1 − ∏(1 − impact рисковых признаков)
итоговый риск услуги = базовый риск × ∏(1 − impact защитных признаков)

score клиента = 100 × max(риски его действующих услуг)
лояльность = 100 − score
```

Объединение рисковых сигналов устроено по схеме noisy-OR. Например, сигналы с impact 0,54 и 0,70 дают `1 − 0,46 × 0,30 = 0,862`. Защитный impact 0,30 уменьшит результат до `0,862 × 0,70 = 0,6034`.

Защита уменьшает риск относительно его текущего значения, а не вычитает баллы. Если рисковых сигналов нет, защитные причины скрываются. `impact` в карточке — параметр формулы, а не независимая прибавка к score.

Пороги по умолчанию: **высокий ≥ 70**, **средний ≥ 40**, иначе низкий. Зона риска объединяет высокий и средний уровни. При сортировке по score по убыванию равные оценки дополнительно упорядочиваются по ожидаемым потерям по убыванию.

Score отражает наиболее проблемную услугу клиента; он не является отдельной вероятностью полного ухода аккаунта. «Лояльность» — обратная шкала того же индекса.

### Денежная оценка и действия

```text
выручка услуги по прайсу = цена × горизонт / длительность периода

возраст клиента = время от создания самой ранней услуги, минимум 1 день
платёжеспособность = доступные средства
                   + totalReplenished / возраст клиента × горизонт

выручка клиента = min(сумма выручки по прайсу, платёжеспособность)
потери клиента = Σ(риск услуги × её скорректированная выручка)
```

При ограничении платёжеспособностью выручка распределяется по услугам пропорционально их выручке по прайсу. Ограничение можно отключить через `capRevenueByCapacity`. Для приведения цен используются средние длительности месяцев и годов; расписание продлений строится календарно.

Например, при выручке услуг €80 и €40 после ограничения и рисках 0,8 и 0,2 потери клиента равны `€80 × 0,8 + €40 × 0,2 = €72`, а его score равен 80.

Потери услуги распределяются между рисковыми признаками пропорционально их impact. Это способ объяснить оценку, а не доказанный причинный эффект; из-за округления возможны небольшие расхождения итогов. Защитным признакам потери не приписываются.

Рекомендация выбирается по рисковой причине с наибольшим impact среди услуг клиента: напомнить об оплате, пополнить баланс, включить автопродление, проверить оплату, выяснить причину выключения или помочь с первым продлением. Если главная причина — нехватка средств, а клиент пополнил за всё время не меньше `bigSpenderThreshold` (€1000 по умолчанию), предлагается персональное предложение.

### График оттока

График показывает удалённые услуги, ожидаемое число непродлений и число услуг с риском от среднего порога.

- Прогноз размещается на дате истечения услуги; для `prolong_wait` добавляется период ожидания. Прошедшая дата переносится на дату расчёта. Ожидаемое число непродлений — сумма рисков услуг в интервале.
- Для наблюдаемого перехода в `deleted` берётся дата из журнала. Для старой удалённой услуги без истории используется `expiresAt`, ограниченный моментом расчёта: это приближение, не известная дата удаления.
- При длине графика до 120 дней используются дневные интервалы, при большей — недельные.

## Архитектура

```text
React + TypeScript → nginx / Vite proxy → FastAPI
                                           ├── импорт и валидация снимка
                                           ├── расчёт риска → сводка, график, метрики
                                           ├── Repository → память / JSON-файлы
                                           └── SSE → повторные запросы открытых страниц
Prometheus ───────────────────────────────→ /metrics
```

| Каталог или файл | Назначение |
|---|---|
| `backend/main.py`, `config.py` | Запуск, конфигурация, таймер, health и metrics |
| `backend/models.py`, `domain.py` | Исходные сущности, результаты и общие типы |
| `backend/risk/` | Признаки, формулы, агрегация и рекомендации |
| `backend/routers/`, `schemas.py` | API, схемы запросов и ответов |
| `backend/services/` | Нормализация, upsert, журнал, пересчёт, SSE и метрики |
| `backend/repository.py`, `repository_file.py` | Протокол хранилища, память и файловая реализация |
| `backend/security.py`, `deps.py` | Хеширование пароля, JWT и проверка сессий |
| `frontend/src/` | Страницы, компоненты, API-клиент и SSE-подписка |
| `data/` | Снимки, генераторы и SQL-артефакты |
| `deploy/` | Конфигурация Prometheus и правила алертов |
| `openapi.json` | Сохранённая спецификация API |

При запуске выполняется первичный пересчёт, далее — после импорта, сохранения настроек и по таймеру каждые 60 секунд. Таймер пересчитывает текущий снимок, но не забирает данные из внешней системы: источник должен отправлять PUT/PATCH.

Файловый репозиторий сохраняет `snapshot.json`, `model_settings.json`, `journal.json` и `sessions.json`. Результаты риска восстанавливаются пересчётом. Файлы заменяются через временный файл и `os.replace`; общей транзакции между ними нет.

### Пример работы с API

Нужны `curl` и Python 3. Пример использует демонстрационные учётные данные; при смене пароля замените их в запросе.

```bash
API=http://localhost:8000
TOKEN=$(curl --fail-with-body -sS "$API/api/v1/auth/login" \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"admin"}' \
  | python3 -c 'import json, sys; print(json.load(sys.stdin)["access_token"])')

curl --fail-with-body -sS "$API/api/v1/customers?level=high,medium&sort_by=score&sort_order=desc&limit=10" \
  -H "Authorization: Bearer $TOKEN"

curl --fail-with-body -sS -X PATCH "$API/api/v1/model/settings" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"weights":{"insufficient_funds":0.5}}'

curl --fail-with-body -sS -X PUT "$API/api/v1/source/snapshot" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  --data-binary @data/data_realistic.json
```

Список поддерживает `search` по email, `level` (например, `high,medium`), `sort_by`, `sort_order`, `limit` от 1 до 500 и `offset`. Поля сортировки: `accountId`, `email`, `balance`, `totalReplenished`, `score`, `expectedLoss`, `revenue`, `loyalty`. CSV ограничен 100 000 строками данных.

Файловый endpoint принимает `.json` размером до 50 МиБ по настройке бэкенда. В nginx также установлен лимит тела запроса `50m`; для больших данных нужно согласованно изменить оба ограничения.

Спецификация текущего процесса всегда доступна в `/api/v1/openapi.json`. После изменения API обновите файл репозитория:

```bash
.venv/bin/python - <<'PY'
import json
from pathlib import Path
from backend.main import app
Path('openapi.json').write_text(
    json.dumps(app.openapi(), ensure_ascii=False, indent=2) + '\n',
    encoding='utf-8',
)
PY
```

## Конфигурация

Основные параметры бэкенда находятся в `backend/config.py`. Для локального запуска они читаются из окружения и `.env`.

Compose передаёт только переменные, перечисленные в `docker-compose.yml`: `ADMIN_*`, `JWT_SECRET`, `METRICS_TOKEN`, параметры OIDC, а также фиксированный `STORAGE_BACKEND=file`. Чтобы поменять остальные настройки контейнера, добавьте их в `backend.environment` через Compose или override-файл. Например, одна строка `RECOMPUTE_INTERVAL_SEC=120` в корневом `.env` без такой передачи интервал контейнера не изменит.

| Параметр | Значение бэкенда по умолчанию | Назначение |
|---|---|---|
| `STORAGE_BACKEND` | `file` | `file` или `memory`; у `memory` всё теряется при перезапуске |
| `DATA_DIR` | `var` | Каталог JSON; в Docker задан `/var/lib/churn` |
| `SEED_FILE` | `data/data.json` | Первичная загрузка; в Docker `/app/data/data.json` |
| `SEED_ON_STARTUP` | `true` | Загрузить seed, если хранилище пусто |
| `RECOMPUTE_ON_STARTUP` | `true` | Пересчитать при запуске |
| `RECOMPUTE_INTERVAL_SEC` | `60` | Период фонового пересчёта; 0 отключает таймер |
| `REALTIME_ENABLED` | `true` | Разрешить фоновый таймер |
| `JWT_EXPIRE_MINUTES` | `480` | Срок токена и сессии |
| `METRICS_TOKEN` | пусто | Пустое значение открывает метрики; Compose задаёт токен |
| `MAX_UPLOAD_BYTES` | `52428800` | Лимит чтения загружаемого JSON-файла |
| `JOURNAL_MAX_EVENTS` | `50000` | Ограничение журнала |
| `CORS_ORIGINS` | localhost и 127.0.0.1, порты 3000 и 5173 | Разрешённые origins, JSON-массив |

Базовый `JWT_SECRET` для локального бэкенда — `change-me`, для Compose — `change-me-in-production`. Оба значения нужно заменить при внешнем развёртывании.

OIDC включается при заданных `OIDC_ISSUER` и `OIDC_CLIENT_ID`. Дополнительно доступны `OIDC_CLIENT_SECRET`, `OIDC_PROVIDER_NAME` и `OIDC_REDIRECT_URL`. Для reverse proxy задайте явный callback вида `https://example.org/api/v1/auth/oidc/callback` и зарегистрируйте его у провайдера. Локальный парольный вход остаётся доступен.

В `deploy/alerts.yml` заданы правила: недоступность анализатора, отсутствие пересчёта, доля высокого риска выше 50%, потери выше €10 000 и доминирование одного признака выше 80% потерь. Правила видны в Prometheus; отправка уведомлений через Alertmanager не настроена.

## Как добавить признак

Добавьте функцию с декоратором в `backend/risk/features.py`. Например, рисковый признак пустого основного баланса:

```python
@feature("empty_balance", "Пустой основной баланс", 0.2,
         "Основной баланс равен нулю")
def empty_balance(service, ctx):
    if ctx.account.balance != 0:
        return None
    return Signal(1.0, "Основной баланс равен нулю")
```

Это пример механизма расширения; перед включением признака проверьте его бизнес-смысл и пересечение с `insufficient_funds`.

Регистрация автоматически добавит признак в расчёт, настройки весов, объяснения, сводку и метрики. Для защитного признака укажите `kind="protective"`. Для собственного действия добавьте соответствие в `backend/risk/actions.py`; иначе используется «Связаться с клиентом».

Новый параметр модели добавляется в `DEFAULT_SETTINGS`, валидацию `merge_settings`, схемы `SettingsOut`/`SettingsPatch`, преобразование ответа и типы/форму фронтенда. Добавьте проверку ожидаемого поведения в `backend/tests/test_risk.py` и при изменении API обновите `openapi.json`.

Другой тип хранения подключается реализацией `Repository` и выбором реализации в `build_repository()`; сейчас доступны только память и JSON-файлы.

## Ограничения текущей версии

- Веса и пороги экспертные, точность на размеченных реальных исходах не измерена. Сигналы могут быть зависимы; score нельзя трактовать как откалиброванную вероятность ухода.
- Платёжеспособность использует средний темп пополнений за всё время. Сезонность, изменения бюджета, скидки и эффективность действий удержания не моделируются.
- Исторические даты удаления без наблюдаемого перехода приближённые. Анализатор не меняет статусы услуг автоматически.
- Файловое хранилище, SSE и состояние приложения рассчитаны на один процесс бэкенда. Несколько workers/реплик требуют общей базы, согласования пересчётов и общей доставки событий. Параллельные изменения и пересчёты пока не защищены общей транзакцией или проверкой версии.
- Сессии сохраняются, но пользователи — только в памяти; администратор создаётся заново при старте. OIDC-пользователи не имеют устойчивого хранения, связывание выполняется по имени. Для многопользовательской эксплуатации необходимы постоянные идентификаторы и привязка по `issuer + sub`.
- Импорт не проверяет уникальность ID внутри входных массивов. Передавайте по одной записи на ID; при интеграции с внешним источником нужна дополнительная проверка уникальности.
- `/health` проверяет живость процесса, но не гарантирует успешность последнего расчёта. Для наблюдения за пересчётом используйте логи и метрики.

## Демонстрация за три минуты

1. **Обзор:** покажите распределение риска, потенциальные потери и топ клиентов.
2. **Карточка:** выберите клиента с понятной причиной, разберите услугу и рекомендуемое действие.
3. **Настройки:** измените один сработавший вес и дождитесь обновления score и денег без перезагрузки. Верните настройку после демонстрации.
4. **Обоснование:** модель объяснимая, оценка клиента берётся по наиболее рискованной услуге, потери складываются по услугам. Следующий этап — сбор истории и проверка прогнозов на фактических продлениях.
